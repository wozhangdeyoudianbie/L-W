# L-W 性能与压测说明

测试时间：2026-08-22 至 2026-08-25

## 1. 测试目的

本轮压测用于验证：

- 大量TCP客户端能否完成连接和JOIN；
- 持续MOVE与快照广播下是否出现协议错误；
- 失败时能否定位阶段、原因和客户端；
- 服务器与LoadGen是否存在明确的CPU瓶颈。

本轮测试不是为了得到生产环境的最大在线人数。

## 2. 测试环境与负载

测试环境：

- Linux虚拟机
- 4个逻辑CPU
- 服务器与LoadGen运行在同一台虚拟机
- TCP回环地址127.0.0.1
- 服务器端口8080
- 文件描述符上限1048576

负载参数：

- 每个房间4名玩家
- 每秒建立100个连接
- 每名玩家每100ms发送一次MOVE
- 心跳周期2000ms
- warm-up 10秒
- measure 60秒
- drain 2秒

## 3. 历史容量扫描

未附加性能采集工具时，2000、3000、3500、4000和4300客户端曾完成完整工作负载。

4300客户端结果包括：

- 连接成功率100%
- JOIN成功率100%
- MOVE约43000帧/秒
- 快照约86000帧/秒
- 协议错误0
- 意外断开0
- Tick编号缺口0
- 心跳RTT p99为27.712ms
- 快照间隔p99为77.429ms
- 快照间隔最大值为105.767ms

4600客户端发生失败，但当时的LoadGen不能在失败后生成报告，因此不能确定具体失败阶段。

4300成功、4600失败只是当前同机环境中的历史实验区间，不能写成服务器最大支持4300人。

## 4. 失败可观测性

本阶段为LoadGen增加了第一次失败报告，内容包括：

- 失败阶段；
- 失败原因；
- 客户端编号；
- 失败时active客户端数量；
- 系统调用和errno；
- 服务器ERROR帧中的请求类型和错误码。

LoadGen现在无论成功还是失败，都会尝试生成summary.txt。

## 5. 性能采集结果

附加pidstat和perf后，4000客户端测试结果为：

- 4000个客户端全部连接成功；
- 4000个客户端全部JOIN成功；
- 连接失败0；
- JOIN失败0；
- 协议错误0；
- 意外断开0；
- 第一次失败发生在measure阶段；
- 失败原因为MOVE的already_submitted；
- 失败时active客户端数量为4000；
- 心跳RTT p99为19.093ms；
- 快照间隔p99为71.085ms；
- 快照间隔最大值为166.813ms；
- LoadGen调度延迟最大值为98.222ms。

平均资源数据：

- 服务器CPU约59.73%，即约0.60个CPU核；
- base线程CPU约16.61%；
- LoadGen CPU约57.29%，即约0.57个CPU核；
- 服务器内存约36MB；
- LoadGen内存约45MB。

没有线程表现为持续占满一个CPU核，也没有内存耗尽证据。

## 6. 失败原因解释

服务器保持以下业务约束：

> 一名玩家在一个逻辑Tick中最多提交一条命令。

高负载下同时观察到：

- LoadGen发送调度出现延迟；
- 服务器快照间隔超过正常50ms Tick周期。

因此，同一客户端的两条MOVE可能进入同一个服务器逻辑Tick。

第一条MOVE尚未从Room的pending_commands_中取走时，第二条MOVE到达，服务器返回already_submitted。

该拒绝保护了房间状态，不能通过删除这项检查来提高压测数字。

## 7. 最终结论

本轮证据不能证明服务器CPU先饱和，也不能证明LoadGen CPU先饱和。

能够确认的是：

> 服务器与LoadGen位于同一台虚拟机时，高负载会产生调度和Tick时序抖动，第一次明确失败是MOVE违反每名玩家每Tick一条命令的约束。

因此，本阶段不修改服务器线程模型、Room、Tick或协议，也不继续扫描更多客户端数量。

如果未来需要测量服务器独立容量，应当：

1. 将服务器和LoadGen部署到不同机器；
2. 固定代码版本、硬件和负载参数；
3. 记录服务器内部任务等待和Tick处理时间；
4. 区分帧已排队、已写入socket、已被服务器接受和已完成结算；
5. 使用多次实验报告稳定区间，而不是单次最大值。
